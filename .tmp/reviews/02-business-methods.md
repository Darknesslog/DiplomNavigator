## Три критических пути: фактические маршруты

`POST /applications` и `PATCH /applications/{id}/approve` в приложении отсутствуют.
Новые алиасы для этих примеров не добавлялись: ниже указаны существующие контракты.
`current_load` вычисляется COUNT активных Assignment, отдельного обновляемого
счётчика/триггера нагрузки в этих операциях нет.

### Создание заявки

Маршруты: `POST /topics/{topic_id}/applications` и совместимый
`POST /topics/{topic_id}/bookings` →
[create_application](../../backend/app/services/application.py).

1. Роутер разрешает student; зависимость читает текущую роль и активность из БД.
2. Проверяется профиль студента; отдельно сохраняется ранее существующая команда истечения.
3. Тема блокируется `FOR UPDATE`; проверяются наличие, published и кафедра.
4. Блокируется студент; проверяются активное закрепление студента, занятость темы,
   активная заявка этой пары, cooldown и pending-заявка другого студента.
5. Создаются pending-заявка с дедлайном и запись истории; commit с rollback/409
   при IntegrityError. Финальная защита эксклюзивности темы — частичный индекс.

Конкурентная проверка: два студента через два алиаса резервируют одну тему;
ожидаются один HTTP 201, один 409 и ровно одна pending-заявка.

### Одобрение заявки

Маршруты: `PATCH /supervisor/applications/{application_id}/approve`,
`PATCH /reservations/{application_id}/approve`,
`POST /booking-requests/{application_id}/approve` →
[decide_application](../../backend/app/services/supervisor.py) →
[lock_assignment_capacity](../../backend/app/services/workflow.py).

1. Первый и третий маршруты ограничены nauchruk; reservations также разрешает
   zavkaf/admin. Сервис проверяет собственную тему/кафедру для соответствующей роли.
2. После отдельной команды истечения блокируются заявка, тема, руководитель и студент.
3. Заявка должна быть pending, тема published; проверяются роль/активность профилей,
   кафедра, COUNT активных закреплений < max_students, отсутствие конфликтующих закреплений.
4. В одной транзакции сохраняются Assignment, approved-статус, история и уведомление.
   Частичные индексы и обработка IntegrityError обеспечивают окончательный отказ 409.

**Подтверждённый и исправленный дефект:** при ожидании блокировки Teacher уже
находился в identity map после аутентификации. Снижение лимита другой транзакцией
не обновляло это состояние автоматически. До исправления регрессионный тест:
HTTP 200, load=2, max_students=1. После добавления `populate_existing=True`
к блокирующему запросу: HTTP 409, нагрузка остаётся в пределах лимита.

### Изменение лимита

`PATCH /supervisors/{supervisor_id}/limit` →
[update_limit](../../backend/app/services/management.py).

Роутер разрешает admin/zavkaf; сервис проверяет кафедру, блокирует ту же строку
Teacher, что и одобрение, получает актуальную нагрузку. Лимит ниже нагрузки
отклоняется с 409, отрицательный лимит — схемой с 422. После commit возвращаются
карточка руководителя и пересчитанные карточки кафедры. Автоматическое создание
уведомления о перегрузе не реализовано; сам запрет снижать лимит ниже нагрузки есть.

## Проверка границы чтения

В исходном [read_models](../../backend/app/services/read_models.py) обнаружены
вызовы истечения заявок и commit. Команда перенесена в
[application](../../backend/app/services/application.py); API вызывает её отдельно
перед проекциями. Проекции visible_applications, supervisor_dashboard и
head_dashboard теперь выполняют только SELECT, что проверено перехватом SQL
и события commit на реально просроченной заявке. Также проверено сохранение
прежней обработки истечения через API и отсутствие этой команды при запросе
дашборда чужой кафедры.

Это разделение обязанностей модулей, не полный CQRS: GET по-прежнему запускает
прежнюю lazy-expiration-команду на уровне API. Периодический worker потребует
отдельного решения по расписанию и гарантиям выполнения.
