### Подтверждённый дефект: устаревший лимит после ожидания блокировки

Регрессионный тест:
`test_approval_rechecks_limit_changed_while_waiting_for_lock`.

1. У руководителя одна активная работа при лимите 2.
2. Транзакция заведующего удерживает строку руководителя.
3. Руководитель начинает одобрение новой заявки. Аутентификация загружает его
   профиль с ещё действующим лимитом 2, после чего одобрение ждёт блокировку строки.
4. Заведующий через штатный update_limit снижает лимит до 1 и завершает транзакцию.
5. Одобрение получает блокировку, но использует уже загруженный ORM-объект
   Teacher с прежним max_students=2.
6. Фактически возвращается HTTP 200, а активная нагрузка становится 2 при лимите 1.
   Ожидается HTTP 409 и сохранение нагрузки 1.

В lock_assignment_capacity SELECT FOR UPDATE защищает строку от параллельной записи,
но не обновляет автоматически ранее загруженный объект в identity map SQLAlchemy.
Тест синхронизирован через событие выполнения запроса блокировки; случайные задержки
для воспроизведения не используются. Дефект повторно подтверждён через штатный сервис
изменения лимита. Тест оставлен падающим, без xfail; бизнес-код не менялся.

## Подтверждённые особенности текущей логики

1. Статус учебного периода `closed` не препятствует новой заявке на опубликованную тему.
   Ни статус периода, ни окно подачи не проверяются в create_application.
2. После admitted_to_defense можно вернуть активную работу в in_progress и снизить процент.
   Допуск принудительно ставит 100%, но монотонность этапов не обеспечивается.
3. После одобрения одной заявки другие заявки студента остаются pending.
   Попытка их одобрить блокируется наличием активного закрепления.
4. Завершённое закрепление освобождает текущую нагрузку руководителя,
   однако его тема остаётся недоступной для нового закрепления.

Первые два случая зафиксированы как текущее поведение, а не как утверждённые требования.
Третий требует учитывать существующее правило просрочки: оставшаяся pending-заявка
при последующей обработке таймаута может привести к архивированию своей темы.
Бизнес-код в рамках проверки не изменялся.

## Repowise и границы проверки

Выполнены get_answer, обновление локального индекса через
`repowise update --working-tree` и get_change_risk для `6755095^..b038097`.
После обновления индекс соответствует b038097; часть зависимых страниц остаётся
устаревшей из-за лимита каскадного обновления. LLM-синтез не настроен.
Анализ изменений частичный: оценены 64 из 96 изменённых файлов.
Замечания касаются размера и сложности функций, в частности lock_assignment_capacity,
create_application и демонстрационных скриптов. Это сигналы для ревью,
а не доказательства функциональных ошибок.

SQLite подтверждает API-поведение, ограничения и откат данных, но не воспроизводит
SELECT FOR UPDATE. Эти блокировки дополнительно проверены на PostgreSQL 16
описанными выше сценариями. Полная проверка всех возможных порядков конкурентных
операций и сборка Docker-образа приложения не выполнялись.
