## Контекст проекта

DiplomNavigator — система выбора тем и сопровождения выпускных квалификационных
работ. Пользователи: студент, научный руководитель, заведующий кафедрой и
администратор. Основной процесс: создание и публикация темы → заявка студента →
решение → закрепление → сопровождение → защита → архив.

Backend: FastAPI, синхронная SQLAlchemy, PostgreSQL, Alembic, JWT; окружение — uv
и Docker Compose. Frontend пока является отдельным прототипом с локальными
данными. Три ключевые сущности разделены: `Topic` — предложение темы,
`Application` — заявка студента, `Assignment` — факт закрепления.

Для знакомства достаточно [README](../README.md), [архитектуры](architecture.md)
и [схемы процесса](workflow.md). Для проверки деталей доступны [ER](er.md),
[реестр API](api-endpoints.md) и [протокол тестирования](test-summary.md).
Главные вопросы для экспертной оценки — R01–R05 в разделе 4; остальные пункты
помогают оценить порядок дальнейших работ.

Цель ревью — оценить корректность бизнес-операций, транзакций, разграничения
доступа и достаточность тестов; определить критичность проблем и порядок
исправлений. Вопросы, зависящие от правил учебного процесса или состава MVP,
отмечаются отдельно от технических дефектов.

## 2. Дополнительные требования и границы MVP

В [обсуждении PR №10](https://github.com/Darknesslog/DiplomNavigator/pull/10)
предложены следующие направления развития; их приоритеты, сроки и критерии
приёмки пока не определены:

1. Документооборот: загрузка файлов и выгрузка готовых отчётов; отчёты отмечены
   как прямой запрос отдела разработки.
2. Дедлайны по этапам и списки конкретных заданий внутри этапа.
3. Возможность распространить бизнес-логику на курсовые.

В текущем плане файлы ВКР отнесены к Post-MVP, Excel/PDF — к MVP. Перенос файлов
в MVP требует отдельного решения. Для документооборота ещё не определены шаблоны
отчётов, хранилище и порядок согласования документов. Дедлайны, задания по этапам
и поддержка курсовых рассматриваются как предложения дальнейшего развития.

## 3. Функционал против README и заявленного MVP

В последнем столбце указаны технические вопросы и требования, которые необходимо
уточнить. Полномочия участников, обязательность учебных этапов, шаблоны отчётов
и состав MVP требуют подтверждения владельцем процесса.

| Область | Фактическое состояние | Что уточнить |
|---|---|---|
| Авторизация | JWT, четыре роли, роль/активность из БД, cooldown входа | Достаточен ли access token без refresh/revocation для пилота? |
| Каталог | Создание, публикация, просмотр, фильтры, архив; отдельного редактирования карточки нет | Нужен ли PATCH содержимого темы до пилота? |
| Предложение от студента/партнёра | Завкаф/admin вводит тему с источником; у студента нет собственного POST темы | Кто вводит предложение и требуется ли самостоятельная подача? |
| Заявки | Подача, решение, история; одна active-заявка на тему, несколько pending студента до закрепления | Сохраняем ли эксклюзивную бронь темы и несколько параллельных выборов? |
| Закрепления | Одобрение и ручное назначение; лимит и уникальность проверяются транзакционно | Нужны ли приказ, номер и дата как обязательное условие закрепления? |
| Прогресс | Этап/процент, история, допуск, отзыв допуска с причиной, защита и архив | Нужны ли обязательные этапы и дедлайны? Сейчас можно сразу защитить при 100% |
| Уведомления | Решения по заявке/удалению темы, прогресс и отзыв допуска; GET своих записей | События подачи и истечения, получатели, отметка прочтения; дополнительные каналы отдельно |
| Управление кафедрами | GET справочника, назначение кафедры профилю | Включает ли MVP создание/редактирование кафедр? Защита активных связей отсутствует |
| Смена темы | Нет отдельной операции, причины/истории смены закрепления | Кто утверждает, что происходит с прогрессом и старой темой? |
| Отмена/передача | Статус cancelled и причина есть в модели; API отмены/передачи нет | Должны предшествовать смене темы или войти в одну атомарную команду? |
| Excel/PDF | Нет backend-маршрутов и генерации пользовательских отчётов | Шаблоны, поля, роли, фильтры, формат первого релиза |
| Файлы | Таблица attachments есть; upload/download API и хранилища нет | Остаются Post-MVP или переносятся по запросу ревью? |
| Backup | Автоматического задания и подтверждённого восстановления нет | Владелец, место хранения, периодичность, RPO/RTO |
| Frontend | Прототип на локальных данных | Кто и когда подключает API; backend-тесты не подтверждают сквозной UI |

Основное серверное ядро доступно для демонстрации; полный заявленный MVP ещё
не завершён. Реализованные возможности и планируемый объём разделены в
[README](../README.md).

## 4. Предложенный порядок изменений

P1 — решить/исправить до пилота с реальными данными; P2 — следующий согласованный
объём; P3 — после MVP. Для каждого пункта требуется оценить риск, достаточный
объём исправления и способ проверки. Приоритеты и предложенные критерии
подлежат обсуждению; зависимость от бизнес-правила отмечена явно.

| ID | Приоритет | Наблюдение и риск | Решение и критерий приёмки для согласования |
|---|---|---|---|
| R01 | P1 | `PATCH /users/{id}/department` возвращает 200 при pending/active и сохраняет связи со старой кафедрой; воспроизведено для студента и научрука | Определить блокирующие связи. При наличии таких связей — 409, никаких частичных изменений; повторить для одновременного одобрения/перевода на PostgreSQL. Для отсутствия связей — успешный перевод в допустимый факультет |
| R02 | P1 | Прямой `PATCH /topics/{id}/status` архивирует тему с active Assignment; процесс одобрения удаления это запрещает | Единая политика для всех путей архивирования: при active — 409 без изменений и с общей транзакционной проверкой. Уточнить также pending-заявки и конкуренцию с одобрением |
| R03 | P1 | Подача разрешена в `draft`, `archived`, а также `open` после `application_closes_at`; блокируется только `closed` | Утвердить разрешённые состояния, источник времени и границы интервала. Если нужно окно: принимать только open внутри него; проверить оба алиаса, границы дат и отказ без создания заявки |
| R04 | P1 | Просрочка обрабатывается при запросах и архивирует тему; старое описание обещает освобождение темы и уведомление | Сначала утвердить судьбу темы. Затем отдельное расписание, повторяемая безопасная обработка, история/уведомление, мониторинг; определить допустимую задержку, блокировки и размер пакета |
| R05 | P1: решение | Допускается `in_progress/under_review → defended` без допуска; существующие тесты это закрепляют | Утвердить: допуск обязателен или возможна прямая фиксация защиты. При обязательном допуске обновить таблицу переходов и тесты, сохранив отдельный административный отзыв |
| R06 | P1 | Смена темы заявлена в MVP, но отмены/передачи и истории смены нет | Согласовать одну транзакционную процедуру: автор/причина, старое и новое закрепление, нагрузки обоих руководителей, судьба заявки/темы/прогресса. Ошибка должна откатывать всё |
| R07 | P1 | Экспорт Excel/PDF входит в MVP и запрошен в прежнем ревью, реализации нет | Получить эталон каждого отчёта. Зафиксировать поля, период, роли и кафедры; первый пример выгрузки сверить с данными и правами. Не считать CSV заменой Excel/PDF без решения |
| R08 | P1 до данных | Backup не настроен и restore не проверен | Назначить владельца, RPO/RTO, расписание, хранение и доступ. Приёмка — восстановление в отдельную БД и проверка данных/версии миграций |
| R09 | P1: границы | Запрос документооборота конфликтует с Post-MVP для файлов | Решить отдельно файлы и отчёты. При переносе файлов в MVP — определить типы, размер, хранение, версии, права и сроки хранения до реализации |
| R10 | P2 | Уведомления доступны для чтения; нет read-операции и части событий | Согласовать матрицу «событие → получатель → текст/ссылка». Отметка прочтения доступна только получателю, идемпотентна; чужая запись недоступна |
| R11 | P2: границы | «Управление кафедрами» шире текущего справочника | Утвердить CRUD, роли и архивирование; при активных связях не разрушать справочник |
| R12 | P2: решение | В ревью предложены дедлайны и todo по этапам | Зафиксировать тип этапа/задания, автора сроков, перенос, просрочку, часовой пояс и историю. Не подменять это существующим процентом прогресса |
| R13 | P3 | Поддержка курсовых пока предложена как направление | Уточнить ценность и различия процессов; отдельное решение о типах работ и повторных закреплениях по периодам |

R01–R05 исследованы без изменения продуктового поведения.
R01–R03 — наблюдаемые пробелы, R04–R05 также требуют решения владельца процесса.
Предлагается разделить исправления существующих операций и разработку новых
возможностей, чтобы для каждого изменения были отдельные критерии приёмки.

## 7. Дополнительные замечания по авторизации

- Уникальный индекс `lower(email)` есть в ORM и начальной миграции.
- Смена роли не создаёт новый профиль; переход student → nauchruk ограничен
  существующей моделью профилей. Это ограничение описано в контракте.
- HTTPS вне локальной разработки предусмотрен документацией; конфигурация
  production-развёртывания в рамках этой проверки не проверялась.
- Защита от злоупотреблений входом, IP-rate-limit и управление токенами требуют
  отдельной оценки. Тест на проникновение и измерение таймингов не выполнялись.
