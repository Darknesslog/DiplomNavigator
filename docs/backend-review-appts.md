## Цель ревью и основные вопросы

DiplomNavigator — система выбора тем и сопровождения ВКР. Серверное ядро
демонстрируется через Swagger; React/Vite пока использует локальные данные.
Цель ревью — проверить границы бизнес-операций, конкурентный доступ,
разграничение прав и достаточность плана исправлений перед пилотом.

Просьба начать с этих вопросов:

1. Подходит ли разделение Topic / Application / Assignment и текущих сервисов
   для процесса? Какие существенные противоречия модели и операций пропущены?
2. Какой общий порядок блокировок нужен для перевода кафедры, создания темы,
   подачи заявки, решения, ручного назначения и модерации? Достаточно ли
   защиты лимита и уникальности; где возможны обходы или взаимные блокировки?
3. Где локально обрабатывать истечение целевой заявки, чтобы финальная проверка
   срока происходила после блокировок, а expired/история/уведомление сохранялись
   даже при HTTP 409? Как избежать глобальной очистки внутри чужой транзакции?
4. Достаточны ли RBAC и проверки принадлежности? Просьба оценить последствия
   перевода кафедры и смены единственной роли пользователя.
5. Достаточен ли план миграции старых бессрочных pending с аудитом и условным
   CHECK? Какие дополнительные проверки нужны для безопасного применения?
6. Какие PostgreSQL-сценарии следует добавить до пилота и в каком порядке
   исправлять найденные проблемы, затем подключать frontend?

Правила ниже уже согласованы владельцем проекта. Их технические последствия
и способы реализации открыты для ревью; замечания вне подготовленного списка
также нужны. Новый функциональный объём отдельно отделён от исправлений ядра.

## Согласованный контракт первой итерации

| Решение | Целевое правило |
|---|---|
| Q1. Перевод кафедры | Запрет при pending-заявках, active Assignment, темах научрука в draft/published/rejected. Проверки согласованы с конкурентным созданием связей; одной блокировки User недостаточно |
| Q2. Модерация занятой темы | При active Assignment запрещены archived/rejected через любой маршрут: 409 без изменений целевых данных. Штатная защита атомарно делает completed + archived |
| Q3. Окно подачи | status=open и opens_at ≤ now < closes_at; свежее время после необходимых блокировок. Ручное назначение обходит только период, сохраняя остальные проверки |
| Q4. Истечение | Только pending → expired; история и уведомление студенту. Статус Topic не меняется. Повтор не дублирует события; approved не истекает |
| Q5. Защита | Active Assignment, предшествующий admitted_to_defense и 100%. Закрепление, архив темы, история и уведомление изменяются атомарно |
| Q6. Момент решения | После всех необходимых блокировок перечитать актуальное состояние и срок. now ≥ expires_at запрещает одобрение. expired/история/уведомление сохраняются при 409. После проверки до срока commit может завершиться позже |
| Q7. Предложения студента | Перевод также запрещён по proposed_by_student_id для draft/published/rejected. Archived не блокирует по авторству, но pending/active остаются независимыми запретами |
| Q8. Pending при модерации | Pending запрещает archived/rejected через все пути без побочных изменений. Прошедший дедлайн не заменяет обработку истечения; автоматического отзыва при модерации в первой итерации нет |
| Q9. Роль автора защиты | Только nauchruk + ownership. После повышения до zavkaf право теряется и для собственных работ. Это явно принятое временное ограничение; административный PATCH не является обходом |
| Q10. Простой перевод | Меняет только кафедру профиля. Та же кафедра — 200 без изменений после авторизации. Исторические объекты не переписываются. Аудит фактической смены: исполнитель, время, старая и новая кафедры. Перенос связей — отдельная задача |
| Q11. Исключения допуска | Административный обход отложен. Любой обычный PATCH для defended требует допуска. После отзыва допуска нужен повторный допуск |
| Q12. Старые pending без срока | Предварительная инвентаризация, отдельный льготный срок T0 + 14 дней для подходящих записей, отдельный аудит без смены статуса, идемпотентность и условный CHECK — подробности ниже |

Отказ перевода должен возвращать устойчивые причины `pending_applications`,
`active_assignments`, `unclosed_topics`. Формат тела ответа и приоритет при
нескольких причинах см. в [контракте модерации и перевода](topic-department-contract.md).

## Транзакции и критерии приёмки

Текущая защита нагрузки использует общий lock Teacher и подсчёт active Assignment.
Отдельного изменяемого счётчика нагрузки нет. Частичные UNIQUE защищают активное
закрепление студента, неотменённое закрепление темы и активный резерв темы.
Они не заменяют проверки кафедры, времени и переходов статусов.

Сейчас глобальная очистка берёт Application → Topic, решение начинает со Student.
Простое слияние этих операций в одну транзакцию может создать цикл ожидания.
Предварительная очистка также может коммититься отдельно от последующего решения.
Нужен явный согласованный порядок блокировок всех изменяющих команд.

| Область | Обязательная приёмка на PostgreSQL |
|---|---|
| Перевод | Одновременные создание предложения, подача, одобрение и ручное назначение; запрет без частичных записей; тот же department даёт 200 после авторизации; аудит фактической смены |
| Модерация | Оба статуса и все пути, active и pending с будущим/прошедшим сроком; гонки с подачей, назначением и истечением; успешная штатная защита |
| Подача | Все статусы периода; до и ровно на opens_at/closes_at; ожидание блокировки через границу; оба алиаса; сохранение остальных правил ручного назначения |
| Истечение | Два обработчика и повторный запуск; Topic сохраняет статус; одна история и одно уведомление; approved не меняется |
| Дедлайн решения | Ожидание Student/Teacher через expires_at с синхронизацией по событиям. При 409 нет Assignment, но expired и события сохранены; commit после срока допустим при финальной проверке до срока |
| Защита и роли | Запрет без допуска даже при 100%; повторный допуск после отзыва; nauchruk → zavkaf с ранее выданным токеном; ownership; отсутствие административного обхода; атомарность завершения и событий |

## Q12: план обработки старых данных

14 дней — **льготный период**, а не восстановленный первоначальный дедлайн.
Ни инвентаризация рабочей БД, ни миграция в рамках ревью не выполнялись.

1. Получить количество и список pending с expires_at=NULL, статусы тем и связанные
   закрепления. Противоречивые записи вынести на отдельный разбор.
2. Для подходящих записей установить один общий момент миграции T0 + 14 дней.
   Уже заданные сроки не менять. Статус остаётся pending; резерв не освобождается.
3. Сохранить отдельный аудит: ID заявки, NULL до изменения, новый срок, время,
   основание. Не писать фиктивный переход pending → pending в историю статусов.
4. Повтор не продлевает срок и не дублирует аудит. При пакетном исполнении
   сохранить идентификатор операции и общий T0.
5. Новые pending получают срок на сервере. Через Alembic установить ограничение:

```sql
CHECK (status <> 'pending' OR expires_at IS NOT NULL)
```

Всю колонку делать NOT NULL нельзя: ручное назначение создаёт approved без
дедлайна рассмотрения. CHECK нужен и при отсутствии старых кандидатов.
До его валидации все противоречивые pending с NULL должны быть разобраны.
Процедура должна исключать появление новых бессрочных pending между проверкой,
backfill и включением ограничения.

Приёмка: нулевая выборка; несколько кандидатов с одинаковым новым сроком;
неизменность заданных сроков и approved с NULL; повтор; полнота аудита;
отсутствие статусного перехода и освобождения резерва; конкурентное решение
по заявке; откат пары «назначение срока — аудит»; отказ PostgreSQL при прямой
записи pending с NULL.

## Границы и порядок следующих работ

Сначала — согласованные инварианты, транзакции и PostgreSQL-проверки. Затем —
один сквозной UI-сценарий. До реальных данных нужны backup и проверка restore.
Перенос связанных объектов и административный обход допуска в первую итерацию
не входят. Смена темы и Excel/PDF остаются требованиями согласуемого MVP;
файлы, чаты, дедлайны по этапам и курсовые не считаются реализованными функциями.

Существующие ER/API сгенерированы из кода. Наличие attachments не означает
готовность файлового API; is_read не означает наличие операции прочтения.
is_available у Teacher описан как видимость в справочнике: без отдельного
требования не считаем его отсутствующую проверку запретом назначения.
