## Реализованные действия

| Действие | Endpoint | Роль и границы |
| --- | --- | --- |
| Мои студенты, темы и прогресс | `GET /supervisor/works` | `nauchruk`, только свои закрепления |
| Одобрить / отклонить заявку | `PATCH /reservations/{id}/approve`, `/reject` | Владелец-научрук, завкаф своей кафедры, admin |
| Изменить этап / процент | `PATCH /works/{id}/progress` | Только научрук-владелец |
| Изменить лимит | `PATCH /supervisors/{id}/limit` | Завкаф своей кафедры, admin |
| Назначить свободную тему вручную | `POST /assignments` | Завкаф своей кафедры, admin |
| Увидеть решение | `GET /notifications` | Только получатель уведомления |
| Узнать справочные ID | `GET /study-groups`, `/academic-periods` | Авторизованный пользователь |

Полный перечень, включая прежние пути: [api-endpoints.md](api-endpoints.md).
Роли продолжают читаться из БД на каждом запросе; старые токены не сохраняют
ранее отозванные полномочия.

## Транзакционные гарантии

- Одобрение блокирует заявку и тему, затем профиль её руководителя и студента.
- Проверяется `current_load < max_students`, отсутствие активного закрепления
  студента и отсутствие неотменённого закрепления темы.
- Нагрузка вычисляется по `Assignment.status = active`; отдельного
  потенциально рассинхронизированного числового счётчика нет.
- Изменение лимита использует ту же блокировку профиля руководителя.
  Лимит ниже текущей нагрузки отклоняется `409`.
- После изменения возвращается пересчитанная нагрузка всех действующих
  руководителей кафедры. Лимиты остальных руководителей не изменяются.
- Уникальные индексы студента и темы остаются последней защитой от гонок.
  Конфликты commit переводятся в `409` с rollback.
- Решение, история и уведомление коммитятся совместно. Уведомление доступно
  в приложении; email/Telegram не отправляются.
- Ручное назначение создаёт approved Application и Assignment отдельно.
  Оно не крадёт чужую pending-заявку, не снимает лимиты и не отменяет
  существующее закрепление.
- Override завкафедрой означает право решить pending-заявку другого научрука
  своей кафедры. Переписывание уже принятого решения не выполняется.
- Допуск `admitted_to_defense` принудительно устанавливает 100%, но оставляет
  Assignment активным; `defended` при 100% завершает закрепление.

## PostgreSQL и миграции

`uv sync` выполнен. Миграции применены к реальной PostgreSQL 16 в Docker:
`uv run alembic upgrade head`, текущая вершина `b5c8d0e3f712`.
`uv run alembic check`: **No new upgrade operations detected**.

Новые ревизии:

- `a4b7c9d2e601`: один неотменённый Assignment на тему; заменяет более слабый
  индекс активных закреплений темы. При конфликтующих старых данных миграция
  завершится ошибкой, не удаляя записи автоматически.
- `b5c8d0e3f712`: комментарии timeout/archive-полей согласованы с ORM.

В моделях восстановлены индексы, уже существовавшие в прежних миграциях,
включая active-заявки темы и поиск истекших pending-заявок. Условия частичных
индексов SQLite приведены к PostgreSQL для достоверных API-тестов.

Полная [история](migration-history.md), [ER Mermaid](er.md), [SQL](../sql/schema.sql).
Словарь данных и DBML генерируются локально и исключены из Git как дубли
моделей, миграций и схемы SQL.
Генерация: `uv run python scripts/dump_docs.py`,
`uv run python scripts/dump_ddl.py`, `uv run python -m scripts.export_demo_docs`.

Seed: первый запуск создал 30 записей, повторный пропустил все 30.
Пароль seed-пользователей теперь обязателен в `SEED_PASSWORD`, общего
пароля в исходном Python-коде нет. Существующие пароли seed не перезаписывает.

В этой среде локальный PostgreSQL занял `5432`; Docker перенесён на `5433`

Существующий локальный PostgreSQL не изменялся.

## Основная последовательность демо

1. Bootstrap: `uv run python -m scripts.create_admin`.
2. Login admin; `GET /departments`, `/study-groups`, `/academic-periods`.
3. `POST /supervisors`; другой аккаунт руководителя повысить через
   `PATCH /users/{user_id}/role` до `zavkaf`.
4. `POST /students`; сохранить **User ID** и **Student ID** отдельно.
5. Login научрука; `POST /topics` → draft.
6. Login завкаф; `PATCH /topics/{id}/status` → published.
7. Login студента; `POST /topics/{id}/applications` → pending.
8. Login научрука; `PATCH /reservations/{id}/approve` → approved.
9. `GET /supervisor/works` → закрепление, студент, тема, процент.
10. `PATCH /works/{id}/progress` → admitted_to_defense с 100%.
11. Login студента; `GET /notifications`; вызов supervisor/works → 403.
12. Независимая проверка PostgreSQL скриптом persistence.

Для завкаф дополнительно продемонстрировать изменение лимита и ручное
назначение второй свободной темы другому студенту без активного закрепления.
Пошаговые клики и полные JSON: [USER.md](../USER.md).

сообщает 12 moderate в инструментах разработки, high/critical — 0.

Новая история прогресса, серверный отзыв JWT, отчёты и загрузка файлов
не входят в эту задачу. Merge-коммит frontend создан операцией git merge;
реализация и документация подготовлены отдельным коммитом для ревью PR.
