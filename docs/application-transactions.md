# Подача, решение и истечение: Q3 / Q4 / Q6

Основание: опубликованный контракт `bd5e5b8` и согласованный порядок блокировок.
Общие помощники находятся в [locking.py](../backend/app/services/locking.py),
контекст подачи/решения — в [workflow.py](../backend/app/services/workflow.py).

## Порядок и время

| Команда | Порядок первого захвата |
|---|---|
| Подача, решение, ручное назначение | User → Student → Teacher → AcademicPeriod → Topic → Application |
| Отдельная обработка истечения | User → Student → Application; Topic не блокируется |

В каждом уровне строки захватываются по ID. User включает исполнителя,
участников и получателя уведомления; режим FOR SHARE стабилизирует роль и
активность. Профили блокируются FOR UPDATE. Teacher остаётся заблокированным
до commit, включая проверку свежего max_students и COUNT(active Assignment).
AcademicPeriod блокируется FOR SHARE. Целевая и остальные pending-заявки
студента захватываются одной сортированной группой, до финальной проверки.
Повторное чтение уже заблокированной строки не меняет порядок первого захвата.

Обнаруженные до блокировок ID проверяются после захвата. При изменении связей
контекст откатывается и собирается заново, максимум три попытки. Предпосылка
транзакций — PostgreSQL READ COMMITTED.

В PostgreSQL время берётся через clock_timestamp() после всех необходимых
блокировок. now()/CURRENT_TIMESTAMP для дедлайнов не используются: они возвращают
время начала транзакции. SQLite использует UTC-время приложения только для
поведенческих тестов; он не проверяет конкурентные блокировки.

## Q3: подача и ручное назначение

Оба маршрута `POST /topics/{id}/applications` и `POST /topics/{id}/bookings`
используют один сервис. Подача допустима только при status=open и
application_opens_at ≤ now < application_closes_at; иначе 403 без новой заявки.
Сохраняются проверки кафедры, опубликованной темы, уникальности, занятости и cooldown.

Ручное назначение руководством обходит состояние и окно периода, сохраняя права,
кафедральные ограничения, доступность участников, резерв темы, лимит и уникальность.
При успешном назначении/одобрении другие pending студента становятся withdrawn
в той же транзакции, без cooldown и изменения тем. Это относится и к другим
pending с прошедшим сроком, если отдельная команда ещё не перевела их в expired.

## Q4: отдельная команда

```powershell
uv run python -m backend.scripts.expire_applications
```

[Команда](../backend/scripts/expire_applications.py) открывает собственную сессию,
вызывает [обработчик](../backend/app/services/application.py), затем commit.
Низкоуровневый обработчик не коммитит: вызывающий обязан завершить транзакцию,
даже если обработано ноль строк, чтобы освободить родительские блокировки.
SKIP LOCKED применяется последовательно к User, Student и Application.
Кандидаты перечитываются под блокировками, затем снова проверяются pending и срок.

Каждый переход pending → expired сохраняет одну историю и одно уведомление
application_expired студенту с application_id/topic_id. Поля статуса, публикации
и архива Topic сохраняются. Повтор и конкурентный обработчик не дублируют события.
approved/rejected/withdrawn/expired не изменяются. Legacy pending без срока
не получают придуманный срок: это отдельный контракт Q12.

Глобальное истечение удалено из подачи, решения, ручного назначения и всех GET:
список/карточка тем, заявки научрука, applications/me, bookings/me,
booking-requests, оба dashboard научрука и dashboard кафедры. Чтение показывает
сохранённое состояние, включая ещё не обработанную overdue pending.
Фоновое расписание не устанавливается этой реализацией; команду запускает
оператор или внешний планировщик.

## Q6: решение

После захвата всех родителей и группы заявок повторно читаются status/expires_at
целевой заявки и свежее время. Сначала проверяются полномочия. Если pending уже
истекла, сохраняются expired и оба события, выполняется commit, затем выдаётся
HTTP 409. Закрепление и его история не создаются; другие pending не отзываются.
Это явная граница команды, учитывающая autobegin запросов аутентификации.

При живой заявке решение, закрепление, начальная история прогресса, отзыв других
pending и уведомление фиксируются атомарно. Commit после срока допустим, если
финальная проверка прошла до срока. Ошибка целостности откатывает все события
этой транзакции; ошибка сохранения истечения не маскируется как успешно
сохранённое expired.

## Проверки

[Поведенческие проверки](../backend/tests/test_application_timing.py) выполняются
также на мигрированной PostgreSQL через
[интеграционный набор](../backend/tests/integration/test_application_timing_postgresql.py).
Конкурентные случаи используют независимые соединения, Event/Barrier и
pg_blocking_pids; достижение дедлайна проверяется по часам самой БД.

После HTTP-ответа новая сессия проверяет статус/срок заявки, точное число истории
и уведомлений, адресата и payload, неизменность темы, отсутствие Assignment и
истории прогресса при 409. Для успешного позднего commit проверяются approved,
decided_at < expires_at и наличие одного закрепления/событий. Повтор решения
и обработчика проверяется повторным чтением БД.

Проверка 26.11.2026 в общем рабочем дереве: Ruff — успешно; штатный набор —
218 passed; полный PostgreSQL-набор — 250 passed. PostgreSQL запускался в
одноразовом Compose-проекте с полной цепочкой Alembic. Прямой pytest через
выбранный Python использован после ошибки uv trampoline до запуска тестов.
