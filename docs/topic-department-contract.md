# Модерация темы и перевод кафедры: Q1, Q2, Q7, Q8, Q10

## Контракт

`PATCH /topics/{id}/status` запрещает `archived` и `rejected`, если у темы есть
хотя бы одна `Application(pending)` или `Assignment(active)`. Тот же guard
применяется при `PATCH /topics/deletion-requests/{id}/approve` **до** изменения
запроса, темы и создания уведомления. Просроченная pending остаётся запретом
до отдельного перехода в терминальный статус. Модерация не запускает истечение.
Отклонение самого запроса архивирования разрешено и не меняет тему.

`PATCH /users/{id}/department` сохраняет прежние ограничения ролей, области
доступа и факультета учебной группы. Авторизованный запрос на текущую кафедру
возвращает `200` и обычный `UserResponse`, не проверяя блокирующие связи и не
создавая запись аудита. Авторизация выполняется до этой проверки.

Фактическую смену запрещают следующие связи, независимо от текущей роли аккаунта:

| Причина | Профиль Student | Профиль Teacher |
|---|---|---|
| `pending_applications` | Pending по `Application.student_id` | Pending через `Topic.supervisor_id` |
| `active_assignments` | Active по `Assignment.student_id` | Active по `Assignment.supervisor_id` |
| `unclosed_topics` | `Topic.proposed_by_student_id`, статус draft/published/rejected | `Topic.supervisor_id`, статус draft/published/rejected |

Archived-тема не блокирует перевод по авторству/владению, но её pending/active
связи проверяются независимо. Срок pending не участвует в фильтре запретов.
Completed/cancelled закрепления и терминальные заявки сами перевод не запрещают.

## Форма отказа и приоритет

Используется HTTP `409`. Возвращаются **все** найденные причины в фиксированном
порядке `pending_applications`, `active_assignments`, `unclosed_topics`.
`reason` равен первому элементу; порядок не зависит от ID и порядка строк БД.

```json
{
  "detail": {
    "code": "department_transfer_blocked",
    "reason": "pending_applications",
    "reasons": ["pending_applications", "active_assignments", "unclosed_topics"]
  }
}
```

Для модерации форма совпадает, `code` — `topic_moderation_blocked`, возможны
первые две причины. Остальные существующие ошибки (область доступа, отсутствие
объекта, несовпадение факультетов) сохраняют прежний контракт.

## Блокировки и транзакция

Порядок: **User по ID → Student по ID → Teacher по ID → Period → Topic →
Application по ID → Assignment → TopicDeletionRequest → новые события → commit**.
Пропуск ненужных уровней допустим. Все решения принимаются по перечитанным
после блокировки строкам (`populate_existing=True`), включая профиль исполнителя.
Предполагается PostgreSQL `READ COMMITTED`.

Общий [помощник блокировок](../backend/app/services/locking.py) используется
циклом заявки и изменёнными командами:

- User исполнителя, участников и получателей событий берутся заранее в `FOR SHARE`;
  User переводимого аккаунта — сразу в `FOR UPDATE`, без повышения режима позже.
  Это учитывает последующие FK-проверки истории/уведомлений и исключает обратный
  переход от профиля к ранее не заблокированному User.
- Предложение темы блокирует предлагающего Student, затем Teacher руководителя.
  Перевод берёт те же профили до проверки отсутствия связей; профиль исполнителя
  тоже стабилизируется. Созданное первым предложение запрещает перевод.
  Если перевод первый, кафедры проверяются заново; тема с явной прежней кафедрой
  отклоняется. Без явно заданной кафедры используются актуальные данные профиля.
- Topic — общий барьер создания заявок/назначений и модерации. Guard не блокирует
  дочерние Application/Assignment: под Topic достаточно проверить их отсутствие.
  Решение об архивировании блокирует Topic перед TopicDeletionRequest.
- Изменение прогресса и отзыв допуска приобретают родителей перед Assignment,
  чтобы завершение работы не сохраняло прежнее обратное ребро Assignment → Topic.
  Их бизнес-правила не изменены этой задачей.

Перевод меняет только кафедру профиля и добавляет
`department_change_history(user_id, changed_by_user_id, changed_at,
old_department_id, new_department_id)`. Время берётся после блокировок и проверок.
Начальное назначение кафедры сохраняет `old_department_id = NULL`.
Миграция — [e9a4b5c6d7e8](../backend/migrations/versions/e9a4b5c6d7e8_department_change_history.py).
Транзакция одна; ошибки записи откатывают профиль и аудит вместе. Исторические
Topic/Application/Assignment, авторы, владельцы и ссылки не переписываются.

## Проверки

[Контрактные тесты](../backend/tests/test_department_topic_guards.py) выполняются
на SQLite и повторяются на мигрированной PostgreSQL. Проверяются:
pending с будущим/прошедшим сроком, независимый active-запрет, все статусы тем,
сохранённые профили после повышения роли, no-op и авторизация перед ним,
приоритет трёх причин, исторические объекты и rollback при ошибке аудита,
а также при ошибке после flush обеих записей.

[Конкурентные тесты](../backend/tests/integration/test_department_topic_concurrency.py)
используют независимые сессии и оба порядка команд. Первая операция остановлена
после фактического захвата row lock; ожидание второй подтверждается PostgreSQL
через `pg_blocking_pids`, а результат читается третьей сессией:

- перевод студента/руководителя против предложения, подачи, одобрения и ручного
  назначения; для руководителя — также автоматически публикуемая company-тема;
- прямые archived/rejected и одобрение архивирования против подачи, одобрения и
  ручного назначения;
- отсутствие лишних заявок, закреплений, истории прогресса, уведомлений и
  частичного аудита после отказа.

У одобрения уже есть pending, поэтому перевод не может победить при любом
порядке. Published-тема сама запрещает перевод её руководителя; перевод студента
может победить свободную подачу/ручное назначение. Это ожидаемые последовательные
исходы, а не требование, чтобы любая пара операций имела двух возможных победителей.

(из них **36** синхронизированных гонок). PostgreSQL запущен в отдельном временном
